High-Level Narrative

This pipeline is effectively the reverse of the extract pipeline.

The first pipeline did:

D365  --> Blob --> Snowflake


This pipeline does:!!!!

Snowflake --> D365


Its purpose is to take records that have been prepared inside Snowflake and send them back to Dataverse (Dynamics 365) using the D365 Web API.

Think of it as a writeback/orchestration pipeline.

It does not build the requests itself. Instead it:

Reads configuration from Snowflake.
Applies a circuit breaker.
Processes entities (CONTACT, ACCOUNT, etc.).
Calls a child pipeline (PL_D365_DispatchRequests).
The child pipeline sends POST/PATCH requests to D365.
Records success/failure statistics.
Maintains state in the watermark table.

What the Pipeline Does
Step 1 - Read Configuration
LKP_GetConfig


Reads:

AUDIT_DB.CONFIG.PIPELINE_METADATA
AUDIT_DB.CONFIG.PIPELINE_WATERMARK


Obtains:

For example:

ACCOUNT

Step 2 - Circuit Breaker
FLT_CircuitBreaker


If:

CONSECUTIVE_FAILURES >= 5


that entity is skipped.

Purpose:

Avoid continuously posting bad requests
Avoid hammering Dataverse
Protect API limits

Step 3 - Process Each Entity
FE_ProcessEntities


Runs sequentially:

CONTACT
then
ACCOUNT


Notice:

"isSequential": true


This is deliberate.

You often load:

CONTACTS first
ACCOUNTS second


or vice versa depending on dependencies.

The designer clearly wanted predictable ordering.

Step 4 - Mark Entity As Running

Updates:

AUDIT_DB.CONFIG.PIPELINE_WATERMARK


Sets:

STATUS = RUNNING
START_TIME
RUN_ID


This provides monitoring and auditing.

Step 5 - Call Child Pipeline
PL_D365_DispatchRequests


This is where the actual work happens.

The description says:

Reads pending POST/PATCH requests
from VW_D365_REQUESTS


Meaning Snowflake already contains prepared API requests.

Something like:

REQUEST_ID
ENTITY
METHOD
PAYLOAD


Example:

{
   "firstname": "John",
   "lastname": "Smith"
}


and

PATCH CONTACT 12345


or

POST ACCOUNT


The child pipeline sends them to Dataverse.

Step 6 - Success

If everything completes:

SCR_MarkSuccess


Updates watermark table:

STATUS = SUCCESS
FAILURES = 0
ROWS = requests sent

Step 7 - Failure

If writeback fails:

SCR_MarkFailed


Updates:

STATUS = FAILED
FAILURES += 1
ERROR MESSAGE
RUN ID


Eventually the circuit breaker stops processing that entity.

Why I Think It Was Designed This Way
✅ Decouples Data Processing From API Calls

Business logic happens inside Snowflake:

Matching
Deduplication
Validation
Transformations


Only the final API requests are sent to D365.

✅ Provides Guaranteed Auditability

Every request goes through:

VW_D365_REQUESTS


and every run is recorded in:

PIPELINE_WATERMARK


You can answer:

What was sent?
When?
How many?
Did it succeed?

✅ Protects Dataverse

The circuit breaker prevents:

Bad payloads
Missing references
Configuration errors


from hammering the D365 API indefinitely.

✅ Supports Large Migrations

This looks very much like a migration or integration design.

One-line Summary

PL_D365_Writeback is a metadata-driven Azure Data Factory orchestration pipeline that reads pending create/update requests prepared in Snowflake, sends them to Dynamics 365 via the Dataverse Web API, and records success, failure, and circuit-breaker state in Snowflake for controlled, auditable writeback processing.
