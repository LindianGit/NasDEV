This one is a much more enterprise integration pattern than a simple ETL pipeline. It is effectively an MDM Writeback Engine that takes approved Golden Records in Snowflake and synchronises them back into Raiser's Edge.

The Big Picture

                 |  MDM Golden Records  |
                 +----------+-----------+

                 +----------------------+

                            |
                            v
            +----------------------------+
            | PL_RE_DispatchRequests     |
            +----------------------------+
                            |
            +---------------+---------------+

            v                               v
       POST Create                   PATCH Update

            +---------------+---------------+

                    Raiser's Edge

What Problem Is It Solving?

Imagine the NAS MDM platform has determined:

Golden Record
-------------
John Smith
Address Updated
Email Updated
Phone Updated


The business wants those changes pushed back into:

Raiser's Edge


This pipeline performs that outbound synchronisation.

Step 1 - Read Pending Requests
LKP_GetRequests

Reads from:

INTEGRATION_DB.RAISERS_EDGE.VW_RE_REQUESTS


The best thing about this design is that ADF is not building payloads.

Instead:

Snowflake
     ↓
Generates URL
Generates HTTP Method
Generates JSON Body
     ↓
ADF executes it


Example rows:

HTTP_METHOD = POST
REQUEST_URL = /constituents
REQUEST_BODY = {...}


or

HTTP_METHOD = PATCH
REQUEST_URL = /constituents/12345
REQUEST_BODY = {...}


ADF acts purely as an orchestration engine.

That is a very clean architecture.

Mary Jones

The POST sends:

POST /constituents


with a JSON payload.

Blackbaud returns:

PATCH Scenario

Suppose:

Mary Jones
already exists

new phone number


was added.

Then:

PATCH /constituents/845211


updates the existing record.

No duplicate constituent is created.

What I Like Architecturally
✔ Metadata Driven

Snowflake knows how to build requests.

ADF only executes.

Very maintainable.

✔ Reusable Authentication

Authentication is centralised.

No duplicate OAuth logic.

✔ Supports Create and Update
POST
PATCH


through one framework.

✔ Golden Record Based

Everything revolves around:

GOLDEN_RECORD_ID


which is classic MDM design.

✔ Reverse Synchronisation

Capturing newly created IDs is excellent integration practice.

Without this you'd keep creating duplicates.

Things I Would Challenge
1. Sequential vs Parallel

The biggest issue.

Description:

Sequential


Code:

isSequential = false


Those conflict.

2. Secure Output

Almost everything is:

secureOutput = false


including token-related activities.

I'd strongly consider:

secureInput = true
secureOutput = true


for security.

3. Token Refresh Placement

At first glance, the token refresh activities appear inside the request-processing branch structure.

I'd check whether a token is being refreshed more often than necessary.

Ideally:

Get Token Once
      |
      v
Process Hundreds of Requests


rather than:

Request
 ↓
Get Token
 ↓
Request
 ↓
Get Token

Interview-Level Summary

If I were explaining this to a client or architecture panel:

PL_RE_DispatchRequests is an outbound MDM synchronisation
pipeline. It reads pending REST API requests generated by a
Snowflake metadata view, retrieves a valid Blackbaud SKY API
access token, and dispatches POST or PATCH requests to
Raiser's Edge. New constituent identifiers returned from
POST operations are written back into cross-reference tables,
allowing future synchronisation cycles to perform updates
rather than inserts. The design separates business logic from
orchestration, with Snowflake generating request payloads and
ADF acting purely as the execution layer.


Of all the pipelines you've shown so far, this is the one that most clearly demonstrates senior data engineering and MDM integration design, because it is implementing a complete end-to-end writeback framework rather than simply moving data between systems.
