-------------------------------

This pipeline is much simpler than the previous ones.

Its job is not to move business data.

Its job is to extract metadata about SQL Server tables and their primary keys.

What It Does

The pipeline runs a SQL query against SQL Server system tables:

sys.tables
sys.schemas
sys.indexes
sys.index_columns
sys.columns
sys.key_constraints
sys.types


and extracts information about every table that has a primary key.

It retrieves:

Schema Name
Table Name
Primary Key Name
Primary Key Column Name
Column Order
Data Type
Length
Nullable Flag


Then writes the results to:

Azure Blob Storage


as a CSV file.

Example Output

Suppose SQL Server contains:

CREATE TABLE dbo.CONTACT
(
    CONTACT_ID INT PRIMARY KEY,
    FIRST_NAME VARCHAR(50),
    LAST_NAME VARCHAR(50)
);


The CSV may contain:

SchemaName,TableName,PrimaryKeyName,ColumnName,KeyColumnOrder
dbo,CONTACT,PK_CONTACT,CONTACT_ID,1


For composite keys:

PRIMARY KEY (ORDER_ID, LINE_NUMBER)


you may get:

dbo,ORDER_LINE,PK_ORDER_LINE,ORDER_ID,1
dbo,ORDER_LINE,PK_ORDER_LINE,LINE_NUMBER,2

Why Do I Think It Exists?

This is where it gets interesting.

Given your NAS migration project, I'd say there are three likely reasons.

1. Build Migration Mapping Documents (Most Likely)

When migrating from Raiser's Edge to D365, someone needs to know:

What tables exist?
What are the primary keys?
How do records link together?


This extract creates a catalogue.

Example:

CONSTITUENT
ADDRESS
PHONE
EMAIL
GIFT
CAMPAIGN


and their identifying keys.

Essentially:

Source System Data Dictionary

2. Generate Metadata-Driven Pipelines

The D365 extract pipeline you showed earlier is heavily metadata-driven.

A common approach is:

Step 1
Discover source tables

Step 2
Store metadata

Step 3
Generate ingestion processes automatically


This metadata CSV might later be loaded into:

PIPELINE_METADATA


or another control framework.

3. Support Data Modelling

One of the first things a data modeller asks is:

What uniquely identifies a record?


Primary keys answer that.

Without this information you can't easily build:

Joins
Dimensions
Fact tables
MERGE statements
Deduplication logic

What It Does NOT Do

Unlike the D365 pipelines, it does NOT:

Move customer data
Load transactions
Update records
Maintain watermarks
Track failures
Send API requests


It's simply extracting structural information.

Think:

Metadata


rather than:

Business Data
