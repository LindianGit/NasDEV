
This pipeline is essentially the SQL Server equivalent of your D365 extract pipeline.

If I had to summarise it in one sentence:

It uses metadata stored in Snowflake to extract data from Raiser's Edge SQL Server tables into Azure Blob Storage, supporting both full and incremental loads with watermarks, retry protection and circuit-breaker logic.

What It Does

Unlike PL_SQLServer_ExtractTablesMetadata (which extracts metadata about tables),

this pipeline extracts the actual business data.

Examples:

CONSTITUENT
ADDRESS
PHONE
EMAIL
GIFTS
EVENTS
CAMPAIGNS


from Raiser's Edge SQL Server.

Step-by-Step
1. Read Metadata Configuration
LKP_GetConfig


Reads from:

AUDIT_DB.CONFIG.PIPELINE_METADATA
AUDIT_DB.CONFIG.PIPELINE_WATERMARK


For each configured entity it retrieves:

Source Table
Source Query
Load Type
Delta Column
Watermark
Staging Path


Example metadata row:

ENTITY_ID      = CONSTITUENT
SOURCE_TABLE   = dbo.CONSTITUENT
LOAD_TYPE      = INCREMENTAL
DELTA_COLUMN   = DATE_CHANGED

2. Circuit Breaker
FLT_CircuitBreaker


Removes entities with:

CONSECUTIVE_FAILURES >= 5


Why?

To stop:

Broken table
Missing permissions
Bad SQL
Corrupt object


from failing forever.

3. Parallel Processing
FE_ProcessEntities


Processes:

up to 5 entities simultaneously


Example:

CONSTITUENT
ADDRESS
PHONE
EMAIL
GIFTS


all running together.

4. Mark Running

Updates:

PIPELINE_WATERMARK


with:

RUNNING
RunId
Previous Watermark

5. Extract Data

This is the clever bit.

The SQL generated depends on the metadata.

Option A - Custom Query

If:

SOURCE_QUERY exists


it uses:

SELECT ...
FROM ...
JOIN ...
WHERE ...


whatever has been configured.

Option B - Full Load

If:

LOAD_TYPE = FULL


it generates:

SELECT *
FROM dbo.CONSTITUENT

Option C - Incremental Load

If:

LOAD_TYPE = INCREMENTAL


and the current watermark is:

2026-11-01 18:00


it generates:

SELECT *
FROM dbo.CONSTITUENT
WHERE DATE_CHANGED >
      '2026-11-01 18:00'


Only changed rows are extracted.

6. Write To Blob

Instead of JSON:

D365 Extract -> JSON.GZ


this pipeline writes:

Avro


Example:

raisers-edge/
202611/
20261108/
14/
constituent_20261108_141500.avro

7. Update Watermark

For Incremental Loads

It executes:

SELECT MAX(DATE_CHANGED)
FROM dbo.CONSTITUENT


and stores:

MAX_WATERMARK


in:

PIPELINE_WATERMARK


so next run starts from there.

8. Failure Handling

If extraction fails:

Watermark Reverted
Failure Count Increased
Error Saved


Exactly like the D365 extract pipeline.

Why I Think It Exists

Looking at all the pipelines you've shown, I think the overall NAS architecture is:

Raiser's Edge
      |
      v
SQLServer_MetadataDriven
      |
      v
Azure Blob (Raw Landing)
      |
      v
Snowflake
      |
      v
Business Rules
Matching
Deduplication
Golden Records
      |
      v
VW_D365_REQUESTS
      |
      v
D365_Writeback
      |
      v
Dynamics 365


In other words:

Pipeline 1
PL_SQLServer_MetadataDriven


Gets data out of Raiser's Edge.

Pipeline 2
Snowflake Transformation Layer


Cleans and maps the data.

Pipeline 3
PL_D365_Writeback


Pushes the cleansed records into Dynamics 365.

That's why this pipeline looks so similar to the D365 extract pipeline. They were probably built from the same metadata-driven framework, one for SQL Server sources and one for Dataverse sources.
