FUTURE STATE - POST-MIGRATION SNOWFLAKE, MDM AND DYNAMICS
=========================================================
Companion to CURRENT_STATE_DIAGRAM.txt

PURPOSE
-------
This is a target-state view of how the current flow is expected to change after the
Raisers Edge (RE) to Dynamics 365 migration and the RE MDM transition are complete.
It is a design based on the local code, migration specs and NAS talks; it is NOT
evidence that the target objects have been deployed or that the migration is complete.

COMMENT / EVIDENCE KEY
  [COMMENT]   Explains the diagram or a meaningful design change.
  [CODE]      Present in the supplied SQL exports; live deployment may differ.
  [TALK]      Direction described by NAS in the talks.
  [TARGET]    Proposed end-state in the migration specs, not yet verified live.
  [VERIFY]    Needs a business decision, partner detail, test or live-environment check.
  [ONE-OFF]   Migration flow; runs for cutover and reconciliation, then becomes static.
  [DAILY]     Ongoing operational flow after go-live.

  [COMMENT] The three existing scheduled tasks can remain in sequence:
            TK_STANDARDISE_RECORDS -> TK_BUILD_MATCH_GROUPS ->
            TK_GENERATE_GOLDEN_RECORDS. The task schedule itself does not remove
            RE dependencies; the source procedures, matching, survivorship and XREF
            handling must all be changed and validated.
  [TARGET]  Put source activation behind configuration rather than commenting ETL calls
            in and out. Freeze RE before disabling its feed, and guard against the
            existing empty-source soft-delete risk.
  [VERIFY]  Make SP_VALIDATE_MDM part of an agreed monitored validation step. The
            current exports show it outside the three-task chain.
  [VERIFY]  Confirm the Dynamics known issue is fixed, the returned ID is captured,
            and payload/state-table dependencies exist in TEST and PROD before rollout.


3. TARGET ONE-OFF MIGRATION - FLOW B: TRANSACTIONS / REFERENCE DATA
--------------------------------------------------------------------

  Frozen Raisers Edge history
  gifts, events, participants, memberships, tax and other in-scope entities
             |
             v
  Agreed Mapping V6 + source/default decisions + cut-off criteria
             |
             +--> unresolved / unmapped / unsafe rows --> HOLD / exception reason
             |
             v
  Reference and lookup payloads
             |
             v
  Resolve each supporter through:
       legacy RE ID -> crosswalk -> GOLDEN_RECORD_ID -> Dynamics supporter ID
             |
             v
  Build entity payloads (no person matching / golden-record generation here)
             |
             v
  ADF hand-off -> Dynamics landing zone / API
             |
             v
  Record success, failure, returned IDs; reconcile each entity; retry safely

  ORDER (each stage released after the prior stage reconciles):
    1. Reference / lookup data
    2. People and organisations (Flow A creates or resolves supporter IDs)
    3. Address, consent, relationships
    4. Events, then participants
    5. Payment schedules and direct debits
    6. Transactions / lines, restrictions, tributes and soft credits
    7. Tax declarations
    8. Memberships, commitments and enquiries
    9. Final delta, reconciliation, then freeze RE

  [COMMENT] Flow B is not another MDM feed. It carries the already-resolved supporter
            ID as a foreign key so transactional records point to the right Dynamics
            person or organisation.
  [VERIFY]  Mapping coverage, cut-off rules, gift splits/codes and the Dynamics-side
            payload contract remain prerequisites. Open questions should hold rows,
            not silently omit them or guess values.
  [COMMENT] Once the final delta and acceptance checks pass, Flow B is static; it does
            not become a daily transaction-sync process in this target design.


4. WHAT CHANGES FROM THE CURRENT-STATE DIAGRAM
----------------------------------------------

  Current diagram element                    Target-state treatment
  -----------------------------------------  ----------------------------------------
  ADF full-copy RE feed / STG_T_*            Final snapshot, then stop the live feed.
  SP_ETL_RAISERS_EDGE in daily wrapper       Freeze first; disable; remove only later.
  RE-<CONSTITUENT_ID> as identity anchor     Retain historical link in crosswalk/XREF;
                                             match through validated shared identifiers.
  SP_ETL_DYNAMICS marked OFF                 Fix known issue, map gaps, test, then enable.
  STANDARDISED_RECORDS with RE + HubSpot    HubSpot + Dynamics active sources; RE history
                                             is frozen/archive, not refreshed.
  Golden record survivorship by recency      Use an agreed source-priority policy and
                                             verify field-level parity.
  Contact/Account payloads in DEV            Promote and verify all dependencies across
                                             DEV, TEST and PROD before production use.
  Gifts/events/memberships/tax without       Add one-off Flow B mapping, gates, payloads,
  complete payload route                     state, write-back and reconciliation.
  RE-dependent XREF / validation             Preserve historical IDs; revise RE-specific
                                             measures and validate retained-source links.
  Unverified Dynamics write-back            Persist outcomes and returned Dynamics IDs
                                             so future runs PATCH/link rather than duplicate.

  [COMMENT] "Remove RE" means remove it as an ongoing operational dependency, not erase
            historical RE identifiers or discard the final source snapshot before
            audit, lookup, parity and cut-over requirements are met.


5. CUTOVER GUARDRAILS - DO NOT SKIP
-----------------------------------

  BEFORE changing production:
    [ ] Verify live task state, deployed DDL, XREF capture and payload dependencies.
    [ ] Capture a reproducible baseline of standardised records, match groups,
        golden IDs/values, XREF and payload counts.
    [ ] Seed and test the legacy-ID crosswalk; confirm the Dynamics legacy-ID field.
    [ ] Resolve required field sources/defaults and sign off losses and cut-off rules.
    [ ] Fix and validate the Dynamics organisation matching issue in TEST.
    [ ] Run RE-frozen and HubSpot/Dynamics MDM paths in parallel in TEST.
    [ ] Compare stable golden IDs, member sets, match outcomes, field values,
        duplicate/orphan XREFs, payloads and inactivation counts against agreed thresholds.
    [ ] Reconcile Flow B by entity, including record counts, financial totals,
        supporter links, holds, exceptions and Dynamics responses.

  ROLLBACK / RETIREMENT:
    Phase 1-2: restore the RE source flag if a tested rollback is needed.
    Final retirement: stop RE feeds only after parity and production acceptance;
    remove RE code after the agreed cooling-off period, retaining the archive and
    legacy crosswalk required for historical lookups.

  [COMMENT] These are proposed acceptance guardrails from the draft specs, not evidence
            that the checks have passed. Proposed numeric tolerances require NAS sign-off.
