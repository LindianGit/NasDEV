2. THE HAND-OFF CONTRACT (THE "UP UNTIL ADF" LINE)
--------------------------------------------------

  Snowflake gives ADF, per Dynamics entity:            ADF gives Snowflake back:

  +--------------------------------------+             +---------------------------------+
  | entity | POST or PATCH | key         |             | row key | success / failure     |
  | JSON body | hold reason | batch id   |  ------->   | error text | Dynamics ID        |
  | (max 2,000 rows per entity per run)  |             | (stored in the state table)     |
  +--------------------------------------+             +---------------------------------+


3. TWO FLOWS (THE MAIN IDEA OF THE SPEC)
----------------------------------------

  +------------------------------------------+   +------------------------------------------+
  | FLOW A - SUPPORTERS                      |   | FLOW B - TRANSACTIONS AND REFERENCE DATA |
  | Contact, Organisation, Address, Consent, |   | Gifts, Payment Schedules, Direct Debits, |
  | Relationship, Title, Connection          |   | Events, Participants, Membership, Tax,   |
  |                                          |   | Appeals, Packages, Campaigns             |
  |------------------------------------------|   |------------------------------------------|
  | Goes through the MDM (de-duplicate)      |   | Does NOT go through the MDM              |
  | Runs DAILY, continues after go-live      |   | ONE-OFF migration (trial loads, fixes,   |
  | Needs Spec 1 (Raisers Edge removal)      |   | final delta, then static)                |
  | Mostly mapped (Contact ~63/73 required   |   | About half mapped (Transaction 16/35,    |
  | fields have a source)                    |   | Participant 10/34, Tax 1/14)             |
  +--------------------+---------------------+   +---------------------+--------------------+
                       |                                               ^
                       |   Dynamics ID of each supporter               |
                       +-----------------------------------------------+
                       Flow B needs Flow A first: a gift cannot be loaded
                       until its supporter exists in Dynamics.

5. LOAD ORDER (EACH STEP RELEASED ONLY WHEN THE PREVIOUS ONE RECONCILES)
------------------------------------------------------------------------

   1. Reference and lookup data
        |
   2. People and organisations (Flow A)  --> Dynamics ID written back
        |
   3. Address, consent, relationships
        |
   4. Events, then participants
        |
   5. Payment schedules, direct debits
        |
   6. Transactions and lines, restrictions, tributes, soft credits
        |
   7. Tax declarations (Gift Aid window rule still ASSUMED)
        |
   8. Memberships, commitments, enquiries
        |
   9. Final delta load at cut-over, then FREEZE Raisers Edge
